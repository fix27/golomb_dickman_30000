## Что именно гарантируется

Программа считает интеграл в шарах Arb (интервальная арифметика с
произвольной точностью) и печатает **середину** итогового шара. Каждый узел,
каждая частичная сумма и итог — шары, поэтому ошибки округления всех операций
учтены автоматически. Итоговый шар имеет радиус `10^-30058`, а печатаются
30000 знаков, т.е. погрешность почти на 58 порядков меньше половины последнего
напечатанного разряда: **все 30000 знаков верны** (при условии, что верна
модель ошибки квадратуры — см. ниже).

Проверки этого прогона:

* `verify/audit_30000.txt` — 21 узел в списке (равномерно по индексам плюс
  характерные `u`, от `10^-690` до `≈tol`), 19 сверено независимым путём
  (выше точность, `+288` бит, другой режим `E1`), 2 пропущены как меньшие
  допуска: расхождение `10^-30049…10^-60109` при допуске `10^-30047`, все `ok`;
* `verify/chunk_radii_run_v3.txt` — сертификация «по кускам»: из 289 кусков ни
  один не шире `10^-30003`, худший `10^-30054`;
* `verify/t300b.log`, `t1000b.log`, `t2000b.log` — регрессия на 300/1000/2000
  знаках: шар `10^-357` / `10^-1057` / `10^-2057` при порогах
  `10^-303` / `10^-1003` / `10^-2003`, сверка первых 99 знаков с OEIS — `OK`;
* `verify/t2000cfb.log` — тот же расчёт 2000 знаков с принудительно другим
  способом счёта `E1` (цепная дробь вместо автоматического выбора): цифры
  совпали посимвольно;
* `verify/crosscheck.txt` — сверка с независимым Python-результатом (его копия
  входит в поставку: `verify/lambda_30000_fix_python.txt`) и, если они есть
  рядом, с более ранними файлами проекта (см. ниже).

```cmd

```

```cmd
chunk_radii.exe run_v3 30000
powershell -ExecutionPolicy Bypass -File verify\crosscheck.ps1
```

Проверка целостности поставки: `sha256sum -c SHA256SUMS.txt` (из MSYS2,
`C:\msys64\usr\bin`) — проверено, все 19 файлов `OK`.
В PowerShell то же самое можно сделать через `Get-FileHash`.

Опции программы: `--guard`, `--const`, `--jobs`, `--chunk`, `--ckpt`, `--out`,
`--e1 auto|expint|cf`, `--audit N`, `--plan`, `--check`. Коды возврата:
`0` — шар в допуске, `2` — шар шире допуска (файл помечается
`*** НЕ ПОДТВЕРЖДЕНО ***`), `3` — не пройден аудит, `1` — ошибка.

## Метод

1. Квадратура Такахаси-Мори: подстановка `u = exp(t - e^{-t})`,
   `du = u(1 + e^{-t}) dt`, трапеции по `t` с шагом
   `h = const / ((digits+guard) ln 10)`, `const = 8`, `guard = 30`.
   Подынтегральная функция `F(u) = exp(-u - E1(u))` целая, `F(u) ~ u` при
   `u -> 0` и `F(u) ~ e^{-u}` при `u -> +inf`, поэтому трапеции сходятся
   экспоненциально.
2. Точность каждого узла своя, `~(tol + ln F)/ln 2` бит, `tol = T + 30`,
   `T = (digits+guard) ln 10`.
3. `E1` нужна с абсолютной точностью `e^{-tol}`; при `2u ≳ tol` она
   отбрасывается (`E1 < e^{-u}/u`, вклад `< e^{-2u}`): в `e1_auto` порог
   `2u ≥ tol`, в `node()` — `2u > tol+60`. Для `u < 1` вместо `E1`
   используется целый ряд `F = e^gamma u exp(V(u))`.
4. Для `u >= 1` `E1` считается тремя способами — это главная техническая
   часть работы:

   | диапазон (N=30000, `prec=99989` бит) | способ |
   |---|---|
   | `u < 0.08·prec` (≈8000) | `arb_hypgeom_expint` при `pe = tol/ln2 + 256` (не выше `prec+4096`) |
   | `0.08·prec ≤ u < 0.13·prec` | степенной ряд `E1(z) = -γ - ln z - Σ(-z)^k/(k·k!)`, `pp = P + 128 + z/ln2 + 32` |
   | `u ≥ 0.13·prec` | цепная дробь с модифицированным алгоритмом Lentz |

   Почему три: у FLINT-функции `arb_hypgeom_expint(1,u)` абсолютная ошибка
   растёт как `~2^-pe·e^u`, т.е. относительно нужной (`E1 ~ e^-u/u`) она теряет
   `2u/ln2` бит. Поэтому `pe = nb + 2u/ln2 = tol/ln2` — **постоянная** величина
   (измерено: при `u=1000` нужно `+2885` бит, при `u=5000` `+14427`, при
   `u=10000` `+28854` — ровно `2u/ln2`). Но даже с правильной `pe` `expint`
   практически висит при `u >= 11000` (>45 с на узел), поэтому выше 0.08·prec
   включаются ряд и цепная дробь.
5. Чётные и нечётные узлы суммируются раздельно; `Delta = 2h|S_even - S_odd|`
   даёт эмпирическую оценку ошибки квадратуры `~Delta^2 = 10^-37041`.
6. Куски узлов раздаются потокам (сначала дорогие — с большим `u`), каждый
   готовый кусок пишется в чекпоинт; сборка частичных сумм и десятичная печать
   тоже в шарах Arb.

## Границы гарантии (честно)

Что доказано:

* ошибки округления всех операций — в шаре, их радиус `10^-30058`;
* усечение ряда `V(u)` при `u<1` и усечение асимптотического ряда `E1` при
  больших `u` ограничены первым отброшенным членом (ряды знакопеременные), и
  это `≤ e^{-tol}·2^-20` на узел;
* обрыв цепной дроби — по критерию `|delta-1| < 2^-(pe+8)`, где `pe = nb+48`;
  ошибка контролируется шаром итерации (стандартная практика, но не формальное
  доказательство остатка);
* отбрасывание `E1` при `2u > tol+60` даёт ошибку узла `< e^{-2u} < e^{-tol}`.

Что является **оценкой**, а не строгой границей:

* ошибка дискретизации квадратуры (`10^-37041`) получена из `Delta^2` —
  эмпирический критерий, а не доказанная оценка;
* сходимость цепной дроби (см. выше).

Поэтому достоверность 30000 знаков опирается на три независимых аргумента:
(1) радиус шара `10^-30058` для всей арифметики, (2) оценку дискретизации
`10^-37041` (на 7000 порядков лучше радиуса), (3) посимвольное совпадение с
отдельной реализацией на другом языке (Python + python-flint: `E1` считается
на 200000 бит от `u.mid()`, при больших `u` — ноль), у которой свой шар
`10^-30058`. Первые 99 знаков совпадают с OEIS A084945.

## Почему это пришлось пересчитывать

Прежние файлы этого проекта (`lambda_30000_cpp.txt`, `lambda_30000_clai.txt`)
несли в заголовке

```
ball.radius=10^-20042   *** НЕ ПОДТВЕРЖДЕНО ***
```

— самопроверка сработала правильно: интервал был в ~10⁴ раз шире нужного.
Причина — заниженная точность `E1` (просили `pe = nb+48` вместо
`nb + 2u/ln2`; потеря ~`2u/ln2` бит, при `u ≈ 1.2e4` это ~10⁴ знаков) плюс
прогон со **устаревшим бинарником** (ошибка компиляции была проглочена,
т.к. в `cmd` цепочка `&` не останавливается на ошибке).

Сверка (`verify/crosscheck.txt`; «первое» = индекс в строке `0.`+цифры,
30002 = совпадение на всех 30000 знаках):

| файл | что это | шар | первое расхождение |
|---|---|---|---|
| `verify/lambda_30000_fix_python.txt` | Python `golomb_dickman.py`, 23.10 (копия в поставке) | `10^-30058` | **30002 (совпадает)** |
| `lambda_30000_cpp.txt` | прежний C++, 25.10 | `10^-20042` | 20046 |
| `lambda_30000_clai.txt` | прежний Python | `10^-20042` | 20046 |
| `30000/out/lambda_30000_fixed.txt` | `main_fixed.py`, 15.10 | нет шара | 22911 |
| `30000/out/lambda_30000.txt` | `main.py`, 13.10 (отозван) | нет шара | 15002 |

Строки, кроме первой, относятся к файлам, лежащим рядом с `pub/` (в полном
каталоге проекта); в самостоятельной поставке скрипт пометит их `MISSING`.
Первая строка воспроизводится всегда — копия независимого результата включена.
Вместе с ней в поставку входит и его исходник —
`verify/reference/golomb_dickman.py` (Python + `python-flint`; именно он дал
`verify/lambda_30000_fix_python.txt` за 17 198 с).

Показательный момент: прежние `cpp` и `clai` совпадают друг с другом
посимвольно на всех 30000 знаках — и оба неверны с позиции 20046. Совпадение
цифр у двух реализаций одного метода не заменяет сертификации шаром.

## Английский abstract

> We present the Golomb–Dickman constant
> `λ = ∫₀^∞ exp(−u − E₁(u)) du = 0.6243299885435508709929363831…` (OEIS
> A084945) to **30 000 decimal digits**, computed with interval arithmetic
> (FLINT/Arb) and certified by the radius of the enclosing ball:
> `ball.radius = 10^-30058` against the required bound `10^-30003`. The
> computation uses Takahasi–Mori double-exponential quadrature on
> `u = exp(t − e^{−t})` with 186 661 nodes. The key numerical difficulty is
> `E₁`: FLINT's `arb_hypgeom_expint` loses `2u/ln2` bits of relative accuracy
> (its absolute error grows like `2^-pe·e^u`) and stalls for `u ≳ 11000` at
> 10⁵-bit precision, so `E₁` is evaluated by three methods (expint, power
> series, continued fraction) with a constant required precision
> `pe = tol/ln2`. The result agrees digit-for-digit with an independent
> implementation (Python + python-flint) that is certified by its own ball
> (`10^-30058`), and the first 99 digits agree with OEIS A084945. Discretisation
> error is estimated (not rigorously bounded) at `10^-37041` via the
> even/odd-sum difference.
